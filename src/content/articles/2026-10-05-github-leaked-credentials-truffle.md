## 何が分かったか

セキュリティ企業 Truffle Security は、LLM の学習用データセット「The Stack v3」に含まれる約2億2,455万の公開 GitHub リポジトリを調べ、見つかった認証情報を2026年7月に発行元サービスで実際に試した。その結果、54万3,699件が認証に通る状態だった。同じ認証情報が複数ファイルやフォークに含まれる分を数えると、露出は110万件を超える。

有効な認証情報が公開されてからの期間は中央値で784日。最も古いものは2009年6月に更新されたファイル内のデータベース認証情報で、調査時点でも使えたという。

## Push Protection の限界

GitHub は2024年2月から公開リポジトリで Push Protection を既定で有効にしている。対象となる種類の認証情報は、有効化前後12カ月の比較で100万ファイルあたりの検出数が53%減った。それでも、今回の有効な認証情報のうち約20万件は2024年2月以降に公開されたもので、51.8% はデータベース接続文字列や Google API キー、秘密鍵など標準設定では止められない種類だった。

発行元による差も大きい。npm トークンは約10万件のうち有効なのは1件だけだった一方、Google Cloud のサービスアカウント認証情報は約12.7万件中6.9万件が有効だった。漏えいを検知して自動で失効させる仕組みがあるかどうかが差を生んでいると Truffle Security は分析している。

## 現場で見るところ

誤ってコミットした認証情報は、検知されたかどうかに関係なく漏えいしたものとして扱い、まず失効と再発行を行い、そのあとで Git 履歴を整理するのが基本だ。Push Protection が既定で有効になる前のコミットは自分でスキャンし、できるだけ有効期限付きの認証情報に切り替えたい。
