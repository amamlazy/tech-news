## どんなコラムか

Tably の及川卓也氏が＠IT で連載する「及川卓也からエージェント時代の開発者たちへ」の第13回（10月8日公開）。9月に登場した TypeSafe AI の判断専用モデル「Jev」を取り上げ、Jev が返す情報、それが「回帰」である意味、有効な使いどころを、筆者の会社の問い合わせ窓口を例に考えている。記事の後半は会員限定。

## 筆者の実例: 1時間に1回の問い合わせ窓口

筆者の会社の問い合わせ窓口は、Claude Code の「Routine」機能で運用している。Slack に投稿された問い合わせを毎日7時から20時まで1時間おきに確認し、単なる売り込みは自動でアーカイブする。

同じ判定を Jev で試すと結果は一瞬で返り、Claude Code 経由で Haiku に頼むと約40秒かかった。ただし Claude Code 側はコンテナの起動から始まるので、40秒の大半は起動時間だと筆者はみている。そのうえで、1時間に1回しか動かない窓口では、一瞬か40秒かの差は実務上ほとんど問題にならないと書く。速度差が効くのはどんな場面か、という問いがコラムの軸になっている。

## 主張: 文章応答の3つの課題を確率で解く

筆者は、いまの生成 AI の文章応答には3つの課題があると整理する。

1. 表記の揺れが生じる
2. 境界線上の判断でも単一の答えしか得られず、確信度がわからない
3. 理由まで書かせるとコストが増える

Structured Outputs のような型指定で1つ目は防げるが、確信度を扱う枠組みがないので残り2つは解けない。Jev に渡すのは、判断材料の「state」と、型が定義された問いの2つだけ。返ってくるのは型定義どおりの答え（choice）、全選択肢の確率（probabilities）、分布の偏りを0〜1で表した確信度（confidence）で、余計な文章を出さないので応答も膨らまない。営業と研修依頼の境目にある問い合わせなら、「営業 0.62、研修・講演依頼 0.31」のように迷い具合まで数値でわかる。

## 主張: 確率はずっとモデルの中にあった

筆者は、Jev はまったく新しいアイデアではないと強調する。生成 AI 以前から、スパム判定や問い合わせの分類では専用の分類器が確率を出すのが普通だった。筆者が Google で関わった、アドレスバーに数文字入れた時点で行き先の URL を予測する「NavSuggest」も、入力を選択肢に割り振る分類器と考えられるという。LLM の内部にも次の単語の確率はあり、OpenAI の API には logprobs もあるが、チャット API が文章応答を基本にしたことで、判定も「文章で出させて解釈する」やり方が定着した。

Jev は汎用性を保ったまま確率を返すという原点を示し、その重要性を思い出させた、というのが前半の結論だ。後半では「新しいのは仕組みではなく、データかもしれない」「OpenAI は Jev の機能を取り込んだ」という論点に進む。

## 読みどころ

AI に分類や振り分けをさせている処理は、本当に文章が要るのかを見直すきっかけになる。確信度が取れれば、低いものだけ人に回すといった設計もしやすい。
