ミューテーションテストは、プログラムをわざと少しだけ壊し（例えば `>` を `>=` に変える）、それでもテストが通ってしまうかを調べることで、「テストがどれだけ不具合を見抜けるか」を測る方法です。この記事は、エンジニアのmizchi氏がZennに書いた、解説と自作ツールの導入記事の要約です。

## カバレッジだけでは足りない理由

mizchi氏は、AIに「分岐カバレッジを80％以上にしろ」と頼んで昼食に行き、戻ってマージする、という使い方を例に、「そのヨシッは何を担保しているのか」と問いかけています。カバレッジ（テストで実行されたコードの割合）にも意味はあり、依存ライブラリの更新を安心して行う助けになります。ただ経験上、85％を超えたあたりから費用対効果が頭打ちになり、95％を超えると「テストのためのテスト」になりがちで、むしろ有害だとすら考えているそうです。

## ミューテーションテストの考え方

コードを書き換えたもの（ミュータント）ごとに、テストを実行します。

- **Killed**：テストが落ちた。変更を見抜けた
- **Survived**：テストが通ってしまった。変更を見逃している可能性がある

例として、`n > 3` を判定する関数に「0は3より大きくない」というテストしかない場合、`>` を `<` に変えると落ちますが、`>=` に変えると通ってしまいます。3ちょうどの境界値を確かめるテストが足りない、と分かるわけです。ただし、どんな入力でも振る舞いが変わらない「等価ミュータント」もあるので、生き残ったものがすべて悪いわけではないと注意しています。副産物として、デッドコード（実行されることのないコード）の候補も見つかります。

## 導入手順

既存のStrykerJSは実行時間が長く、Vitest時代に合わないと感じたため、mizchi氏は自作したそうです。型チェックが通らないミュータントを事前に除外し、変更していない部分の結果をキャッシュから再利用します。cookie-esでの計測では、初回の全体実行が12.2秒、1か所変更したあとの差分実行は0.71秒でした。

Node.js 24以上で、Vitest 5のテストが動いているプロジェクトが前提です。

```bash
pnpm add -D @mizchi/mutator
```

対象を絞るなら、プロジェクト直下に設定ファイルを置きます。

```ts
import { defineConfig } from '@mizchi/mutator';
export default defineConfig({
  include: ['src/**/*.{ts,tsx,js,jsx}'],
  exclude: ['src/generated/**'],
  reporters: ['text', 'html', 'json'],
});
```

キャッシュとレポートは `.mutator/` に出るので `.gitignore` に追加し、実行します。

```bash
pnpm exec mutator              # 全体
pnpm exec mutator --since HEAD # 最後のコミットからの変更だけ
pnpm exec mutator --since main # mainブランチからの変更だけ
```

レポートは `.mutator/report/index.html` などに出力されます。設定ファイルの場所を指定する `--config-file` と、Vitest側の設定を指定する `--config` は別物なので注意、とのことです。

## 運用のコツ

ミューテーションテストはミュータントごとにテストを繰り返すため、元のテストが遅いと時間がかかります（10秒のPlaywrightテストに16個のミュータントなら、単純計算で10秒×16回）。そのため、ミリ秒単位で終わるユニットテスト向きで、CIで毎回全件回すより、リファクタリングの道具として使うのがよいとしています。AIはミューテーションツールの結果を見てテストを直すのが上手なので、ぜひ使いこなそう、と締めくくっています。
