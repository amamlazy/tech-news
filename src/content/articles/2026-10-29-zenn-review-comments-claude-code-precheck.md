PR（プルリクエスト）は、書いたコードを仲間に見てもらうための依頼で、そこにつくコメントが「レビュー指摘」です。この記事は、新人エンジニアが半年分の指摘をClaude Code（AIのコーディング支援ツール）で分類し、自分のチェックに生かした、実践レポートです。

## やったこと

筆者は、3月から8月までの半年分のレビューコメントを、GitHub CLIの次のコマンドで取り出しました。

```bash
gh api "repos/OWNER/REPO/pulls/comments?per_page=100&sort=created&direction=desc&page=1"
```

AIが書いたコメントは除きました。「[MUST]（必須）」「[NITS]（細かい点）」「[IMO]（私見）」のラベルが付いた指摘は、全体の約9%でした。Claude Codeが19種類に分類し、10%を別のエージェントでもう一度分類したところ、92%が一致したそうです。

## 分かったこと

| 指摘の種類 | 割合 |
| --- | --- |
| 既存の規約に揃っていない | 21% |
| テスト不足 | 12% |
| 不具合・考慮漏れ | 10% |
| 不要なコード | 9% |
| 読みやすさ、設計 | 各7% |
| コメント | 6% |
| 命名 | 4% |

必ず直すよう求められた[MUST]だけを見ると、「不具合・考慮漏れ」24%、「規約」16%、「デザインとのズレ」8%、「反映し忘れ」6%、「Issueや設計との違い」5%でした。

## 作ったもの

結果をもとに、PRを出す前に使う「/precheck」スキルを作りました。35のチェック項目と、疑ってかかる14の観点を、Obsidianで管理するMarkdownにまとめたものです。指摘を受けたら新しい発見を追加し、同じ見落としを記録する「/save-review」スキルも用意しています。

## 気をつけたい点

筆者は、スキルは安全網であって、本当は知識を自分の中に入れて、見落とさない人になりたいと書いています。また、すべての項目を手作業で確かめたわけではありません。自分のチームのレビューでも、まずは過去の指摘を集めて数えるところから試せそうです。
