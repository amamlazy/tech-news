## どんな記事か

e-dash の Kezuka 氏による Zenn の実践レポート。Go とクリーンアーキテクチャのバックエンドで、詳しいメンバーのレビューで口伝されていたルールを棚卸しし、AI レビュー用のスキルにして半年運用した結果を測っている。AI 活用でフロントエンドのメンバーもバックエンドを書くようになり、レビュアーが先に詰まりそうだったのが出発点だという。

## 手順: 1,105件のコメントを40ルールに

1. 半年分のマージ済み PR 1,135件から、`.go` に付いたインラインコメント1,105件を集めた。収集とクラスタリングは Claude に任せた
2. 発言者名を消した。「誰の指摘か」を扱わないと決めたことで、議論が人ではなくルールに向いた
3. 週1回集まって1件ずつ採否を決め、40ルール（採用36、不採用2、保留2）にした。採否の軸は「linter や CI で機械的に担保できるか（できるなら不採用）」「文脈依存で固定すると害が出るか」「既存の書き方で十分か」の3つ

## つまずき: チェックリストが膨らんで終わらない

ルールの39件はドキュメントに置き、スキル本体はどのドキュメントを読むかを指す索引にした。ところが参照が2個から23個に増えると、AI が全項目を確かめようとして差分と関係ないコードまで読み始め、1回のレビューが終わらなくなった。

そこでルールごとに「合図になる文字列」を決め、それが差分に出たときだけ該当ルールを開く形に変えた。たとえば `var _ Iface = (*T)(nil)` が差分にあれば冗長かどうかのルールを、`gomock.Any()` があればモックの粒度のルールを開く。文字列の有無だけで決まるものは linter に寄せた。スキルは33回改訂され、約8KB から約19KB になった。

## 結果: 期待は外れたが、一発で通る PR が増えた

- 1 PR あたりのインラインコメント数: 1.32 → 1.32（変化なし）
- 指摘なしで approve された PR: 64.5% → 71.2%
- 変更ファイル数の中央値: 5 → 7（PR は大きくなった）
- 1 PR あたりのレビュー回数: 2.73 → 3.75

筆者は「PR が小さくなっただけ」「approve が形だけになった」という反論を、サイズ帯ごとの集計とレビュー回数で一つずつ退けている。どのサイズ帯でも一発承認の割合は上がっていた。

## 筆者の結論

次の課題は2つ。手元で同じスキルを回しても PR で指摘が出る理由を突き止め、スキルをリポジトリに寄せて実行環境を揃えること。そして PR を小さくすることだ。1〜2ファイルの PR と21〜50ファイルの PR では指摘数が6.8倍違い、これはスキルではなく開発の進め方の問題だとしている。筆者が一番よかったと感じているのは、書かれていない作法をレビューで初めて知る場面が減ったことだという。
