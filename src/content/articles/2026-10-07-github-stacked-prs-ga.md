## 何が変わったか

GitHub は10月6日、スタック PR（stacked pull requests）を一般提供した。大きな変更を、互いに積み重なる小さな PR に分けてレビューし、まとめてマージできる機能だ。GitHub によると、プレビュー期間中にスタックを使ったリポジトリは、使っていない同規模のリポジトリよりマージされたコード量が9%多かった。上位1%のリポジトリの3分の2以上がすでに使っていて、マージまでの時間が5%短くなったという。

一般提供にあわせて、マージとリベースまわりがかなり手直しされている。

- 中身が変わっていないスタックは、ベースブランチが進んだあとに Rebase stack をしても承認が残る。古い承認を取り消す設定のリポジトリでも同じ
- Rebase stack のときに GitHub が署名付きのコミットを作り直すので、元の作者情報も署名も保たれる
- リポジトリルールをバイパスできる人は、スタックのいちばん下にある未マージの PR をその権限でマージできる
- マージキューにはスタック全体が1つのマージグループとして入る。マージコミット方式では、グループ全体で1つではなく PR ごとに1つマージコミットができる
- スタックのベースブランチが削除されても、いちばん下の PR を閉じずに自動で付け替える

## 周辺の改善

PR ページのヘッダーに所属するスタックの情報が常に出るようになり、`Shift`+`J` / `Shift`+`K` でスタック内の PR を行き来できる。`pull_request` Webhook には、PR がスタックに加わったときの `stacked` アクションが追加された。GitHub CLI の拡張 `gh stack` は Git worktree に対応した。スタックの自動マージは今後数週間かけて展開される。

## 現場で見るところ

github.com の全プランで使え、GitHub Enterprise Server には今後のリリースで入る予定。10月1日に一般提供された非同期マージ API と組み合わせると、エージェントやボットが作る小さな PR の列をまとめて流しやすくなる。古い承認を取り消す設定やコミット署名の必須化で、これまでスタック運用をあきらめていたチームは試し直す価値がある。
