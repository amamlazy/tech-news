RAG（ラグ、検索拡張生成）は、AIが回答する前に社内文書などを検索し、その内容をもとに答えを作る仕組みです。「マルチテナント」は、複数の企業（テナント）が同じシステムを共有する形のことで、ほかの会社の文書が絶対に混ざらないようにする必要があります。この記事は、AIエージェントやマルチテナントSaaSの開発経験を持つtakumi_engineer氏がQiitaに書いた実践記事の要約です。

## 考え方

マルチテナントのRAGでは、検索のWHERE句（絞り込み条件）が一箇所抜けるだけで、他社の文書が回答に混ざります。著者は、権限のチェックを「回答が良いか」の評価と混ぜないほうがよいと言います。混ぜると、問題が起きたときに原因を切り分けられなくなるからです。

方針は単純で、各テナントに、ほかでは絶対に出てこない目印（カナリア）の文字列を持つ文書を入れておき、別のテナントとして検索したときにその目印が結果に出たら失敗とします。

## 実装のポイント

検索は `search(tenant_id, role_level, query, top_n)` という1つの関数にまとめます。本番のPostgreSQL＋pgvector（ベクトル検索の拡張機能）では、権限の条件を必ず検索クエリの内側に入れます。

```sql
SELECT doc_id, tenant_id, min_role, text
FROM chunks
WHERE tenant_id = %(tenant_id)s
  AND min_role <= %(role_level)s
ORDER BY embedding <=> %(qvec)s
LIMIT %(top_n)s
```

検索した後にPython側で絞り込むと、上位の枠が他社の文書で埋まってしまう問題も起きると指摘しています。

テストでは、3つのテナントそれぞれに一般向けと管理者向けのカナリア文書（例：`CANARY-A-PUB`、`CANARY-A-ADM`）を用意し、`itertools.permutations` で全テナントの組み合わせを網羅します。肝は、**他社のカナリア文字列そのものを質問に入れる**ことです。キーワード検索でもベクトル検索でも、その文書が最も上位に来やすい状況を作れるからです。あわせて、一般ロールで検索したときに管理者向け文書が出ないこともテストします。

## テストが本当に効くか確かめる

```bash
pytest tests/test_tenant_isolation.py -q
```

次に、検索処理からテナントの条件をわざと消し、テストが全組み合わせで落ちることを確認します。「落ちないテストは、通っても安心材料にならない」と著者は書いています。

## 本番に近づけるには

メモリ上の仮実装ではSQLの書き間違いは見つけられません。著者なら、CIで使い捨てのPostgreSQLを立ててカナリア文書を実際に入れ、本番と同じ検索関数で同じテストを流すといいます。さらに、キャッシュや会話履歴から漏れる経路もあるため、最終的な回答の文章にカナリアが出ないかの検査も1本入れておくのが安全だとしています。

## 落とし穴

- カナリアが自然な文章だと本物の文書とぶつかる。`CANARY-` のような固有の接頭辞を使う
- 管理者ロールだけで試すと、ロール境界の漏れを見逃す
- テナントが2つだけだと組み合わせの不備に気づきにくい。3つ以上にする
- 取得件数が少ないと、漏れても上位に出ないことがある。テストでは件数を大きくする
