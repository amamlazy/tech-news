## どんな記事か

suwa_nobu 氏が10月6日に Qiita に公開した実践レポート。Claude Code 2.1.290 の変更履歴に「WebFetch が10万文字を超えたテキストを黙って捨てていた」問題の修正が載っていた。公式ドキュメントには「一定の文字数で切り詰める」としか書かれていない。そこで修正前の 2.1.289 と修正後の 2.1.290 で、実際に何が変わったのかを計測している。

## 検証の方法

題材は、Claude Code 自身の CHANGELOG.md（約93万文字）。ページ内の位置が分かっている語について、ページに含まれているかを `claude -p --tools WebFetch` で尋ねた。モデルは Opus 5.5、環境は Windows 10。条件ごとに3回ずつ、計36回計測している。

## 分かったこと

- 2.1.289 では、12.5万文字と30.1万文字の位置にある語を「ない」と答えた（6回中6回の誤答）。対照として置いた8.6万文字の位置の語は正しく「ある」と答えた
- 特定の見出しの中身を尋ねると、2.1.289 は内容をでっち上げず「取得できなかった」と答えた
- 2.1.290 は、読めなかった残りの長さと続きを読むための `offset` を注記として返し、Claude はそれを使って10〜11回に分けて読み進め、正しく答えた
- その代わり、費用の中央値は約6倍（0.051ドル→0.314ドル）、時間は約3.8倍（7.7秒→29.2秒）になった。費用の約7割は、取得したページを要約する haiku の処理だった

## 現場で見るところ

筆者は、2.1.290 以降に上げることを勧めている。そのうえで、長いページに「〇〇はある？」と尋ねる使い方は、全文を読むまで答えが出ないのでコストが高くつく、と注意している。検証は1つのページ、1日、各条件3回だけで、HTML のページは試していない、と限界も明記している。長いドキュメントを AI に読ませて「書いていない」と言われたら、取りこぼしを疑うきっかけになる。
