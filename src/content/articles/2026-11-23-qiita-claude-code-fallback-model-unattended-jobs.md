Claude Codeは、AnthropicのAIコーディングツールです。`claude -p "指示"`のように実行すると、画面でのやりとりなしに1回分の作業をこなす「printモード」になり、定期実行（cron や macOS の launchd）と組み合わせて無人で仕事をさせられます。この記事は、合同会社ジョインクラスがQiitaに書いた、無人運用で起きた失敗と対策の実践レポートの要約です。

## 何が起きたか

同社は記事作成や朝のレポートなど30以上のジョブをlaunchdから`claude -p`で動かしています。2026年9月、複数のジョブが同じ時間帯にまとめて失敗しました。原因はコードのバグではなく、主モデルの混雑でした。

## 対策1：--fallback-modelを付ける

```bash
claude -p "今日のログを要約して" \
  --model opus \
  --fallback-model sonnet
```

主モデルが混雑で使えないとき、エラーで終わらずに指定した別モデルで最後まで処理します。「品質が少し落ちても、ジョブが止まるよりずっと良い」という考え方です。主モデルとフォールバック先を同じにしても意味がなく、バージョンによってはエラーになるので、ラッパー側で「主モデルと違うもの」を自動で選ぶようにしています。

## 対策2：全ジョブ共通のラッパーにする

最初は9スクリプト・12カ所に手で入れて回ったそうですが、付け忘れを防ぐため`claude_run`という共通関数に1本化しました。ポイントは次のフラグです。

- `--max-budget-usd 3`：ループの暴走だけを止める、普段は当たらない値
- `--no-session-persistence`：無人ジョブは再開しないので会話記録を残さない（1日約200MBたまっていた）
- `--output-format json`：結果の本文、`is_error`、費用を後ろの処理で読むため

## 落とし穴：利用上限と終了コード

`--fallback-model`が効くのはモデルの混雑だけで、アカウントの利用上限に当たるとどのモデルも使えません。同社では11月15〜16日、毎分起動するジョブが上限エラーで4秒で終わっては再起動するのを約1,000回繰り返しました。上限を判定する正規表現が「You've hit your weekly limit」という文言に当てはまらなかったのが原因です。現在はエラー文を判定して印のファイルを置き、60分は呼ばないようにしています。

また、`claude ... | python3 record-cost.py`のようにパイプでつなぐと、`$?`は後ろのPythonの結果になり、Claude側が失敗しても`rc=0`に見えてしまいます。`PIPESTATUS`を直後に保存し、Claude側の終了コードを優先するように直しています。

## 著者の結論

記事では、利用枠をほとんど使わずに印のファイルや終了コードの動きを確かめるテスト方法も紹介しています。一人で会社を回していると夜中に止まったジョブを直す人はいないため、「落ちない」より「落ちても自分で元に戻る」「落ちるときは無駄に何度も失敗しない」ほうが大事だとまとめています。
